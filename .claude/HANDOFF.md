## 9. Braille-caption / tactile-frame / Avery PDF addendum (2026-07-10, GitHub issue #49, branch `launch-prep/2026-07-10`)

Implemented PROJECT_ROADMAP.md **E5 DRAFT ISSUE (b)** — "Braille-caption & tactile-frame print templates (FPDF) + Avery label sheets" (issue #49), completing the accessible-QR trio started in §8 (#48). Full detail in CHANGELOG.md (Added entry, 2026-07-10, #49) and FEATURES.md (FG-033, now **BUILT**, complete).

- **Built:** a new file `_functions/fn_qr_accessible_pdf.php` implements a `pdf_layout` customisation param (`standard`|`accessible_caption`|`tactile`|`avery_5160`|`avery_l7160`, `format=pdf` only). `standard` (absent/default) is a byte-for-byte no-op, verified via a subprocess test comparing the two request shapes. The other four values bypass the chillerlan `QRFpdf` output class entirely — the raw QR module matrix is obtained via `QRCode::getQRMatrix()` (using the library's own public segment-detection loop, `buildQrMatrixForAccessiblePdf()`) so the code, a large-print caption, a Braille caption, a tactile frame, and/or an Avery label grid can all be composed onto one FPDF canvas. `accessible_caption` = QR + ≥18pt caption + a Grade-1 Braille caption line drawn as geometric dot patterns (`drawFilledCircleOnPdf()` — a pure `Rect()`-strip circle rasteriser, since core FPDF has no circle/ellipse primitive and no Braille-glyph fonts; the maths is unit-tested via `circleStripHalfWidthMm()`). `tactile` adds a second page with CueRCode's own original tactile locator-frame design (`drawTactileLocatorFrame()` — NOT the Thai-patented Chulalongkorn design). `avery_5160`/`avery_l7160` tile the code into Avery label-sheet geometry (`renderAveryLabelSheetPdf()`); a single `/generate` call fills one label, and `fn_api_bulk.php` forks its ENTIRE response (ZIP → a single combined `application/pdf`) when the request-level shared customisation asks for an Avery `pdf_layout` (`bulkRequestWantsAveryLayout()` detects this; `handleBulkAverySheet()` streams it). `pdf_layout` is wired through `buildCustomizationFromRequest()`, the no-JS `index.php` POST fallback, a new UI `<select>` (shown only when format=PDF), `cuercode-generator.js`'s `collectCustomization()`, and `openapi.json` (full enum + the bulk response-shape fork + a new request example). New guidance page `public_html/accessibility/index.php` (linked from the footer) documents the whole print/embossing workflow.
- **Tests:** `tests/test_braille.php`, 65 new assertions — the Grade-1 transliteration table (letters/digits/single-vs-repeated number sign/an ended-then-restarted digit run/punctuation/space/an out-of-scope character rendering as a documented blank cell), dot-geometry helpers, the circle-strip maths (a 3-4-5 right-triangle spot check), the `pdf_layout` enum/param parsing, Avery sheet geometry for both SKUs, caption derivation/truncation, and the bulk Avery-sheet request detector — all pure/in-process. Four subprocess snippets (reusing `test_accessibility.php`'s `runAccessibilitySnippet()` helper, relying on the same documented alphabetical-load-order convention that file itself established) prove: (1) `standard` byte-parity, (2) `accessible_caption`, (3) `tactile`, and (4) `avery_5160` each produce a valid, non-trivial `%PDF`-prefixed document end-to-end through `generateQRCode()`. Full suite: **506/506 assertions green** (was 441/441 before this cycle).
- **Verification run this cycle:** `php -l` clean on all 7 changed/new PHP files + the new test file; `node --check` clean on `cuercode-generator.js`; `openapi.json` re-validated as well-formed JSON; `php tests/run.php` → 506/506. - **Design decisions made without an explicit owner sign-off (flagging per house practice for anything not literally dictated by the issue):**
  1. **Tactile locator frame geometry is entirely my own invention** (10mm margin + 3mm-thick continuous square frame + four 8mm corner "L" registration marks + one 5mm bottom "orientation" dot) — the issue only said "design your own frame geometry... do not clone" the Thai patent; it did not specify dimensions. These numbers are a reasonable first cut, not lab-tested with actual blind users or a physical embosser. **Recommend a physical print/emboss trial with real assistive-tech users before treating this geometry as final.**
  2. **Braille dot pitch/diameter constants** ("Marburg Medium"-approximate: 1.5mm dot, 2.5mm intra-cell pitch, 6.0mm inter-cell pitch, 10mm line pitch) are commonly-cited figures gathered from general Braille-printing knowledge, not sourced from a single authoritative embosser spec sheet (no live web-fetch was performed for this pass). **Recommend verifying against the owner's actual target embosser/swell-paper vendor's spec before high-volume production use.**
  3. **Grade-1 punctuation subset is intentionally small** (period/comma/semicolon/colon/question/exclamation/hyphen/apostrophe) and the capital-letter handling applies a single capital-sign per letter (not the full UEB "passage" double-prefix optimisation for runs of capitals) — both are documented simplifications appropriate for a short caption, not full UEB compliance.

## 16. Saved-codes TOCTOU race fix addendum (2026-07-10, GitHub epic #52/#53, F-023, branch `launch-prep/2026-07-10`)

An INDEPENDENT IDOR review of the §15 saved-codes API (the same stage F-022 came out of) found a SEPARATE, HIGH-severity finding the original ownership/access-control audit did not probe for: a concurrent-request business-logic race, not an authorization gap. Full detail in CHANGELOG.md ("Security / Fixed" entry, 2026-07-10, #52/#53, at the very top of `[Unreleased]`) and SECURITY.md (new F-023 row, FIXED; a new coverage-ledger row for this re-audit pass).

- **The defect:** `handleSaveQRCode()`'s `saved_codes` plan-limit COUNT check and the claim `UPDATE` were two independent statements with zero serialisation between them (classic TOCTOU). N truly-concurrent `POST /save` requests for N DIFFERENT unclaimed UUIDs from the SAME user could each pass the count check before any claim landed - the pre-existing `UPDATE ... WHERE (userID IS NULL OR userID = ?)` guard only ever stopped two requests racing for the SAME `qrID`, never N requests racing for N DIFFERENT `qrID`s under the same cap. **Proven live** (see below): 5 concurrent requests took a cap-2 user to 5 saved codes (2.5× over cap).
- **The fix:** a per-user MySQL SESSION advisory lock - `acquireSaveLimitLock()`/`releaseSaveLimitLock()` (new, `fn_api_qrcodes.php`), wrapping `SELECT GET_LOCK('cuercode_save:<userID>', 5)` / `SELECT RELEASE_LOCK(...)` - now serialises the count-check + claim critical section per caller. Deliberately NOT a transaction + `SELECT ... FOR UPDATE`: the unclaimed row has no owner at SELECT time, so there is no row for row-level locking to lock against this user's *future* claim (a phantom-row problem the advisory lock sidesteps by locking the USER, not a row). `GET_LOCK()`/`RELEASE_LOCK()` share the same `mysqli` connection as the count-check/claim by construction (`dbQuery()` → `getDB()`'s per-request singleton). A `GET_LOCK()` timeout/error fails SAFE (`429 SAVE_LOCK_BUSY` + `Retry-After`, never an unserialised proceed). The lock releases in a `finally` covering every exit path; `handleSaveQRCode()` was restructured to populate an `$outcome` descriptor inside the locked `try`/`finally` and only call `errorResponse()`/`successResponse()` AFTER the lock is released, because both of those functions `exit()` internally and a standalone PHP repro (run this session) confirmed `finally` does NOT execute past an `exit()` call.
- **RE-PROOF (the key evidence — reproduced the reviewer's exact setup):** throwaway scratch MySQL database (dropped after use; DB/encryption credentials as PHP constants via a `php -S` `auto_prepend_file`, never a credentials file), the REAL router served by **5-8 INDEPENDENT `php -S` OS processes** (true parallelism - a single dev-server instance serialises requests and would have falsely looked safe), a plan-capped (`saved_codes: 2`) test account. **BEFORE** (pre-fix code via `git show HEAD` into a separate scratch tree): 5 truly-concurrent `POST /save` calls for 5 different unclaimed UUIDs → **5/5 returned `201`**, DB count confirmed **5 saved codes** for the cap-2 account. **AFTER**: the identical 5-way burst → exactly **2×`201` + 3×`402`**, DB count confirmed **exactly 2**; an 8-way burst (8 independent processes) reproduced the same result. A dedicated fail-safe probe manually held the per-user lock from a separate MySQL session for 8s and confirmed a genuine timeout correctly returns `429 SAVE_LOCK_BUSY` + `Retry-After: 2`, touching zero rows. Serial save→delete→save (freed-slot reuse) and the `-1` unlimited (`business`) plan case were both re-verified working, unaffected by the fix.
- **Tests:** `tests/test_qrcodes.php` gained 20 static, source-text regression-guard assertions (a genuine race cannot be asserted in the dependency-free no-DB harness) pinning the lock's signature, its per-USER scoping, and the never-`exit()`-inside-the-lock invariant. Full suite: **834/834 assertions green** (was 814/814 - +20 new). `php -l` clean on all changed files. `openapi.json` re-validated (16 paths; new `SAVE_LOCK_BUSY` error code + a `save_lock_busy` 429 example on `/save`).
- **Design decision flagged (no further owner sign-off obtained):** the advisory-lock approach was chosen over the task's offered alternative (an atomic `savedCodesCount` counter column on `tblUsers` with `UPDATE ... WHERE savedCodesCount < ?`) specifically for LOWER BLAST RADIUS - no schema migration, and no drift-prone counter needing decrement-on-soft-delete bookkeeping that could itself become a future correctness bug. This is a reversible choice; if the owner later wants the atomic-counter approach (e.g. for cross-datacentre scale where a MySQL advisory lock becomes a bottleneck), it is a self-contained follow-up.
- **Not built/changed:** no schema change; no change to the soft-delete or `-1` unlimited-plan semantics (both re-verified unaffected, see above). GitHub issues were not touched, per this task's explicit "do not touch GitHub issues" instruction.

## 19. SVG logo screening parity on the base64 API path — F-024 companion gap closed (2026-07-10, GitHub issue #52, branch `launch-prep/2026-07-10`)

Closes the gap §18/F-024 explicitly flagged and left unfixed ("queue"d, out of scope for the CSP-hardening task): the multipart `$_FILES` logo-upload path screened SVG content for active/script vectors before accepting it, but the JSON API's base64 `data:image/svg+xml;base64,...` logo path enforced ONLY the F-005 size/pixel caps, so an unscreened malicious SVG logo could reach the generated QR's own SVG output verbatim via `overlayLogoOnSVG()` (which embeds the logo's raw bytes as a nested `<image href="data:image/svg+xml;base64,...">`). Full write-up in SECURITY.md (F-024, "Companion finding — NOW FIXED") and CHANGELOG.md (`[Unreleased]` Security/Fixed entry, top of file).

- **Chose screening-with-parity over a blanket SVG ban** (the task's own preferred option), so SVG logos remain usable via the API — matching option (a) of the three alternatives F-024 itself proposed.
- **`_functions/fn_validation.php`** — extracted the dangerous-pattern SVG check previously hard-coded inline inside `validateImageUpload()` into a new SHARED, pure, unit-testable helper: `screenSvgLogoContent(string $svgContent): array` (returns `['valid' => bool, 'error' => ?string]`). `validateImageUpload()`'s SVG branch now calls it in place of its own inline pattern loop — behaviour for legitimate SVGs is unchanged. The rule set is a SUPERSET of the original 5 patterns (`<script`, `on*=`, `javascript:`, `data:`, `<foreignObject`): it additionally screens `vbscript:` URIs, `<!DOCTYPE`/`<!ENTITY` (XXE / "billion laughs"), CSS `@import`/`expression()`, SMIL `<animate>`/`<set>` elements retargeting an event-handler attribute via `attributeName="on..."` (bypasses a naive static `on*=` scan), and any `href`/`xlink:href` value that is not a same-document `#fragment` reference (blocks `<use>`/`<image>` pulling in externally-hosted content).

## 22. SSO / OIDC client — Microsoft 365 + Google, SIGNula behind a flag (2026-07-10, GitHub epic #55 / children #19/#20/#28, Epic E2, branch `launch-prep/2026-07-10`)

Implements Epic E2 ("SIGNula.id SSO sign-in", re-scoped per the roadmap's own upstream findings: Microsoft 365 + Google ship now as standard OIDC; SIGNula stays behind a flag until it exposes a real OIDC IdP surface, SIGNula issue #88). A generic, provider-agnostic authorization-code + PKCE OIDC client — **every provider is INERT by default**, no real IdP credentials were ever used or needed to build/test this. Full write-up in CHANGELOG.md (`[Unreleased]`, top of file), DEV_NOTES.md ("SSO / OIDC Client"), SECURITY.md (new attack-surface #7 + coverage-ledger row + Remediation log row), FEATURES.md (FG-022 updated to BUILT-partial), README.md (new "Single Sign-On" section).

- **New file `_functions/fn_oauth.php`** (~1,500 lines) — the OAuth2/OIDC client engine, mirroring `fn_auth.php`'s framework-agnostic, plain-array-return convention (no `$_POST`/`$_SERVER` reads, no `jsonResponse()`/`errorResponse()` calls inside the engine itself).
  - **Provider registry**: `ssoSupportedProviders()` (`['microsoft', 'google', 'signula']`), `ssoProviderConfig()`/`ssoProviderIsUsable()` reading tblSettings group `sso` — a MASTER `sso_enabled` kill-switch (mirrors `email_enabled`) PLUS a per-provider `sso_<provider>_enabled` flag, both required, plus non-empty `client_id`/`client_secret`/`discovery_url`, before ANY button renders or ANY flow can start. `signula`'s discovery URL seeds EMPTY on purpose (it is not yet an OIDC IdP — verified against its own repo, see PROJECT_ROADMAP.md) so it stays structurally inert with zero special-case code, regardless of its own enabled flag.
  - **`beginAuth($provider, $nextUrl)`** — validates usability, fetches+caches (24h TTL) the provider's `/.well-known/openid-configuration`, generates a fresh `state`+`nonce` (`random_bytes(32)` each) and a PKCE `code_verifier`/`code_challenge` (S256, RFC 7636), binds all of it + the safe post-login destination + (if the CALLER is already authenticated) the target user-to-link-onto to the PHP session (ONE pending attempt at a time — a new call overwrites any prior one), returns the authorize URL.
  - **`completeAuth($provider, $code, $state)`** — verifies+single-use-consumes `state` (timing-safe, burned on read regardless of outcome — closes the replay window immediately), exchanges code+PKCE verifier for tokens (curl, ≤10s, TLS-verified, secrets never logged), then cryptographically verifies the `id_token`: RS256 signature via the provider's JWKS (fetched+cached, hand-rolled ASN.1/DER JWK→PEM conversion since PHP's openssl extension has no built-in "build key from raw n/e" call, `openssl_verify()` — no Composer, no third-party JWT library) with an EXPLICIT alg-confusion defence (`alg: none` and `alg: HS256` both rejected outright — HS256 specifically defends against using the public RSA key bytes as an HMAC secret, a well-known JWT-library vulnerability class), then `iss` (exact match against the discovery doc), `aud` (== this app's client_id, string OR array), `exp`/`iat` (60s clock-skew leeway), `nonce` (== the session-bound value). Optionally corroborates via the userinfo endpoint (best-effort — a `sub` MISMATCH there is a hard failure, a transport failure is not). Returns the verified subject/email/email_verified/displayName plus an AES-256-GCM-encrypted (`encryptValue()`) token bundle — access/refresh/id_token, never plaintext, never logged.
  - **`decideOAuthAccountLinkAction()`** — the account-linking decision, as a PURE function (no I/O) mirroring `fn_auth.php`'s `computeLockoutExpiry()`/`recordFailedLogin()` pure/DB-wrapper split. THE core anti-takeover defence — see the decision table below. **`applyOAuthAccountLink()`** is the DB-touching wrapper (looks up current tblUserOAuth/tblUsers state, runs the pure decision, applies the resulting INSERT/UPDATE).
  - **`resolveSafeSameSiteRedirect()`** — the open-redirect-proof allowlist (root-relative paths only; rejects `//host`, `https://host`, `javascript:`, any embedded `:` scheme separator, over-length input) — same rule set as `public_html/login/index.php`'s own pre-existing `resolveSafeNextUrl()`, kept as an intentionally separate function here rather than risk touching already-shipped E3 code.
  - **Linked-provider management**: `listLinkedOAuthProvidersForUser()`, `unlinkOAuthProviderForUser()` (IDOR-safe — `userID = ?` in the SAME `DELETE` statement, mirrors `fn_api_account.php`'s `revokeUserSession()`; refuses to remove the account's LAST sign-in credential when no password is set), `userHasPasswordSet()`, `countLinkedOAuthProvidersForUser()`.
- **THE account-linking decision table** (`decideOAuthAccountLinkAction()`, full rationale in its own docblock):
  1. Identity already linked (any flow) → **log the existing linked user in** (re-verification not required on repeat logins).
  2. Not linked yet, unauthenticated flow, IdP email NOT verified → **refuse** (`403 SSO_EMAIL_NOT_VERIFIED`) — never trust an unverified assertion.
  3. Not linked yet, unauthenticated flow, email VERIFIED, a LOCAL account already exists with that email → **refuse auto-link** (`409 SSO_EMAIL_COLLISION`) — THE anti-takeover defence; the visitor is told to sign in normally first and link the provider from account settings (falls into case 5 on that follow-up attempt).
  4. Not linked yet, unauthenticated flow, email VERIFIED, no local account claims it → **create** a new pre-verified account (`status='active'`, `emailVerifiedAt=NOW()`, `passwordHash=NULL`) and link it.
  5. Already-AUTHENTICATED caller, identity not linked anywhere → **link onto the current account** (email verification is irrelevant here — the caller's own session already proves ownership).
  6. Already-AUTHENTICATED caller, identity already linked to THIS SAME account → **no-op success** (idempotent).
