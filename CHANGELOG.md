### Fixed - Bulk-Pipeline Accessibility Parity Close-Out (2026-07-18, #57, FG-033)

Closes the bulk-generation parity gap flagged (but deliberately left open) in `.claude/HANDOFF.md` §8 decision 3: the "Accessible QR" preset (E5 / #48) was fully enforced on `/generate`/`/preview` but silently ignored on `/api/v1/bulk-generate` - a bulk caller could send `preset: accessible` with a sub-3:1-contrast colour pair and receive a QR code `/generate` would have rejected with a `422`. A related CSV/JSON parity gap (7 missing reserved columns) is fixed alongside it, since both surfaced from the same root cause: `fn_api_bulk.php` never called `applyAccessiblePreset()`.

- **Accessible-preset enforcement, both bulk pipelines** (`_functions/fn_api_bulk.php`) - `handleBulkGenerate()`'s ZIP loop and `handleBulkAverySheet()`'s per-item loop now both call `applyAccessiblePreset()` (guarded by `function_exists()`) immediately after `buildCustomizationFromRequest()`, extract + `unset()` the `_accessible_meta` bookkeeping key before it can reach `buildQROptions()`, exactly mirroring `handleGenerate()` Step 3a in `fn_api_generate.php`.
- **Design decision - per-item failure, NOT a batch 422**: unlike `/generate`'s single-item `422 ACCESSIBLE_CONTRAST_TOO_LOW` rejection, a bulk item with a sub-3:1 contrast ratio does NOT abort the request. In the ZIP pipeline it becomes a per-item manifest `[NNN] FAILED type=... reason=Accessible preset rejected: contrast ratio X:1 is below the WCAG minimum of 3:1.` line (that item contributes no ZIP entry); in the Avery label-sheet PDF fork that item's label slot is simply left blank (the pre-existing `422 BULK_AVERY_ALL_FAILED` still covers the all-items-failed case, unchanged). This was a deliberate choice, not an oversight: bulk generation's documented invariant ("individual failures never abort the batch") took precedence over exact parity with `/generate`'s single-item semantics, and no new HTTP error code was introduced. A successfully generated accessible item's ZIP manifest `OK` line is now followed by an additional indented detail line, `accessible: contrast=X:1 (level)`, plus `recommended_print_size_mm=N` when that item also supplied `scan_distance_cm` - real captured values (default black-on-white = `21:1 (pass)`; a genuinely low-contrast pair, `#777777` on `#888888`, = `1.26:1`, below the 3:1 floor).
- **Testable body injection** (`handleBulkGenerate()` signature) - changed to `handleBulkGenerate(array $auth, ?array $requestData = null): void`. **Finding**: `php://input` is a read-once stream tied to the real SAPI request - it cannot be seeded or re-read from CLI PHP 8.5 test code, so there was previously no way to unit-test this function's full ZIP-assembly pipeline (accessible-preset enforcement, manifest formatting, actual `ZipArchive` contents) without a live HTTP server. The router's call site (`public_html/api/v1/index.php`, unchanged - confirmed via `git diff --stat`) still invokes `handleBulkGenerate($auth)` with no second argument, so the pre-decoding body-read block only runs when `$requestData` is `null` - fully backward-compatible, byte-for-byte. Mirrors `fn_api_generate.php`'s `handleGenerate(array $requestData)`, which already receives its body pre-decoded from the router.
- **CSV reserved-column completion** (`CUERCODE_API_BULK_CSV_RESERVED`) - the 20-name list previously omitted 7 of `buildCustomizationFromRequest()`'s recognised keys: `marker_border`, `marker_center`, `quiet_zone`, `version`, `preset`, `scan_distance_cm`, `pdf_layout`. A CSV-only bulk caller had NO way to reach the accessible preset (or any PDF layout, or the marker-shape overrides) at all - only the JSON `items` shape could. All 7 now fold into that row's customization exactly like every pre-existing reserved column.
- **CSV boolean-column coercion fix** (new `bulkCsvCoerceBoolean()`, `fn_api_bulk.php`) - `transparent` and `quiet_zone` are boolean-typed downstream (`buildCustomizationFromRequest()` applies a bare `(bool)` cast), but a raw CSV cell containing the literal text `"false"` previously cast to PHP `true` (PHP only treats `''` and `'0'` as falsy strings) - a pre-existing, silent trap for any CSV caller trying to disable either flag. `bulkCsvCoerceBoolean()` now recognises `false`/`0`/`no`/`off` (case-insensitive) as falsy and everything else as truthy, applied only to those two reserved columns.
- **`openapi.json`** (3 description-only edits, no path/method/schema-shape changes - `test_openapi_render.php`'s router↔spec drift guard only diffs routes, confirmed unaffected): `/bulk-generate`'s operation description gained a paragraph on per-item accessible-preset enforcement and the manifest/blank-slot-not-422 behaviour; `BulkGenerateRequest.properties.csv.description` now lists the full 20 reserved columns and documents the boolean-column coercion; `Customization.properties.preset.description` gained a sentence noting bulk enforcement is per-item and reported via manifest/blank slot, not a 422.
- **Tests (`tests/test_bulk.php`, +33 assertions)**: pure `parseBulkCsv()` coverage for all 7 newly-reserved columns (plus a reserved-only-header still yields `BULK_CSV_NO_INPUT` regression check) and `bulkCsvCoerceBoolean()` (direct + via the CSV fold, mixed casing); an end-to-end ZIP **subprocess** test (`handleBulkGenerate()` driven with 3 items - plain/`preset=none`, accessible+high-contrast+`scan_distance_cm`, accessible+real-low-contrast - captured stdout starting with the ZIP magic bytes, written to a temp file, and inspected in-process with `ZipArchive`: exactly 3 entries, the `Succeeded: 2  Failed: 1` summary, the real `accessible: contrast=21:1 (pass)  recommended_print_size_mm=100` detail line, the real `[003] FAILED ... contrast ratio 1.26:1 ...` line, and a regression guard that item 1's `OK` line carries NO `accessible:` detail); two `handleBulkAverySheet()` fork subprocess tests (one low-contrast item among others still yields a `%PDF`-prefixed sheet; an all-low-contrast request still yields `422 BULK_AVERY_ALL_FAILED`, unchanged). Every asserted substring was captured from a real run before being hardcoded, per this repo's testing convention.
- **Verified**: `php -l` clean on both changed PHP files + the full 175-file tree. `openapi.json` re-validated as well-formed JSON. `php tests/run.php`: **1442/1442 assertions green** (was 1409/1409 - **+33 new**, zero regressions). ### Added - GDPR/CCPA Data-Subject Rights: Account Data Export + Erasure by Anonymization (2026-07-10, #37, epic #52)

Implements the data-subject-rights portion of issue #37 (folded under epic #52): a complete, own-scoped JSON data export and a session-only, password-confirmed, own-account-only account-erasure flow that ANONYMIZES rather than hard-deletes, so financial/audit records (`tblSubscriptions`/`tblPayments`) survive with full referential integrity while personal identifiers are permanently cleared. See DEV_NOTES.md ("Account Erasure: Anonymize Now, Hard-Purge Later") for the full anonymize-vs-hard-purge model and the owner-run purge runbook, and SECURITY.md (new attack-surface §8 + coverage-ledger row) for the complete audit write-up.

- **`GET /api/v1/account/export`** (`_functions/fn_api_account.php` - `handleAccountDataExport()`/`collectAccountExportData()`) - session-only (the SAME F-026 pattern every other `account/*` route enforces: `accountManagementAllowedFor($auth)` refuses an `X-API-Key`-authenticated caller with `403 ACCOUNT_MANAGEMENT_FORBIDDEN` regardless of scope), unconditionally scoped to the caller's OWN `resolveUserIdFromAuth($auth)` userID - there is no field anywhere in this request that could target another account. Returns: profile; saved QR codes (payload + customisation snapshot, NEVER the rendered image blob); sessions (masked identifier + ip/user-agent/times via the existing `listUserSessions()`, NEVER the raw replayable session token); subscriptions + their payment ledger; linked SSO providers (via the existing `listLinkedOAuthProvidersForUser()` - masked subject, NEVER `tokensEncrypted`); and API keys (via the existing `listApiKeysForUser()` - prefix/name/scopes only, NEVER the hash). Sent with `Content-Disposition: attachment; filename="cuercode-data-export.json"`. Rate-limited via the router's existing per-route mechanism.
- **`public_html/account/export/index.php`** (new) - a plain, cookie-only GET companion to the JSON API route (no `X-CSRF-Token` header required - the same justified exception as `account/avatar/`/`account/qr-preview/`: a read has no state-changing side effect for CSRF to protect against, and a plain `<a href>` cannot attach a custom header anyway). Calls the IDENTICAL `collectAccountExportData()` function, so there is exactly one place that decides what an export contains.
- **`POST /api/v1/account/erase`** (`handleAccountErase()`/`eraseUserAccount()`) - session-only (same guard), requires the caller's CURRENT password (`verifyPassword()` - wrong password -> `401 INVALID_PASSWORD`, zero mutation) and an explicit `"confirm": true` in the body (checked BEFORE the password; missing/false -> `400 CONFIRMATION_REQUIRED`, also zero mutation). On success, ONE MySQL transaction: `tblUsers` is ANONYMIZED in place - `email` -> a non-reversible `deleted-<userID>@deleted.invalid` placeholder (`buildErasedAccountEmail()`, RFC 2606 `.invalid` TLD), `displayName` -> `'Deleted user'`, `firstName`/`lastName`/`avatarPath` -> `NULL` (the avatar FILE is also deleted from disk), `passwordHash` -> `NULL` (login becomes permanently impossible), `status` -> `'deleted'`, `erasedAt` -> `NOW()`; ALL sessions revoked; ALL API keys deactivated (soft-revoke, matching `revokeApiKeyForUser()`'s own convention); ALL linked SSO providers unlinked; ALL saved QR codes soft-deleted (the SAME mechanism `DELETE /api/v1/qrcodes/{uuid}` already uses). `tblSubscriptions`/`tblPayments` rows are DELIBERATELY left untouched - they carry no PII beyond the now-anonymized userID FK, and this preserves the pre-existing `ON DELETE RESTRICT` financial-audit-retention posture without a schema change. A double-erase race is guarded (the anonymizing `UPDATE`'s `WHERE` re-checks `status != 'deleted'` in the SAME statement, reporting `409 ALREADY_ERASED` on zero affected rows). Ends the session via `logoutCurrentUser()` on success. The audit-log entry (`account_erased`) is PII-free - only the userID, never the email/name that was just cleared.
- **Schema (`_includes/sql/install.sql`)**: `tblUsers.status` ENUM gained `'deleted'`; new `tblUsers.erasedAt DATETIME NULL` column, documented inline.
- **UI (`public_html/account/index.php`)**: new "Your data" card - a plain "Download my data" link to `/account/export/`, and a "Delete my account" `<form>` requiring (1) the current password, (2) an "I understand this is irreversible" acknowledgement checkbox, and (3) typing the literal word `DELETE` (enforced via HTML5 `pattern="DELETE"` on a `required` input - blocks submission even with JavaScript disabled - AND independently re-checked server-side before `eraseUserAccount()` is ever called). A successful no-JS erasure redirects to `/login/?erased=1`; `public_html/login/index.php` shows a small "Your account has been deleted" confirmation banner on that flag.
- **`privacy.php`**: new Section 11.1 ("Self-Service Access, Export & Erasure") documents the concrete in-account mechanism (and the API endpoints, for developer callers); new Section 7.1 ("Retention After Account Erasure - Anonymization, Not Deletion") documents the anonymize-then-later-purge retention model, with a `[TEMPLATE]`-marked placeholder for the confirmed retention-window length pending counsel review.
- **OpenAPI**: 2 new paths (**27 total**, was 25) - `/account/export` (GET, `CsrfAuth`-only security) and `/account/erase` (POST, `CsrfAuth`-only, documents `CONFIRMATION_REQUIRED`/`INVALID_PASSWORD`/`ACCOUNT_MANAGEMENT_FORBIDDEN`/`ALREADY_ERASED`), plus 9 new component schemas.
- **Tests (`tests/test_account_data.php`, new, 116 assertions, no-DB harness)**: `buildErasedAccountEmail()` pure-function coverage (deterministic, non-reversible, RFC 2606 `.invalid` domain); the two branches of `eraseUserAccount()`/`collectAccountExportData()` reachable with genuinely ZERO database (the `confirm=false` short-circuit runs BEFORE any `dbQuery()`/`getDB()` call; the "DB unavailable" fail-safe paths); source-text regression guards pinning the transaction wrapping, every anonymize/revoke/deactivate/unlink/soft-delete statement, the NEVER-touches-`tblSubscriptions`/`tblPayments` invariant, the NEVER-selects-a-secret-column invariant in the export query, the router wiring (both routes + dispatcher cases), and the OpenAPI `CsrfAuth`-only security declarations. `tests/test_openapi_render.php` updated for the 27-path spec.

### Security / Fixed - Independent OIDC/SSO Security Review Remediation: Unlink TOCTOU Lock + Fail-Closed CSRF + JWK kty/azp/CRLF Hardening (F-027..F-031, 2026-07-10, #55, Epic E2)

An independent security review of the Epic E2 SSO/OIDC client (a DIFFERENT lens than that stage's own self-review - concurrency + spec-conformance, not token/claim/linking correctness) found one Medium finding and four Low defence-in-depth hardenings. All five are fixed in this pass. See SECURITY.md (F-027 through F-031) for the full write-up; summarised here.

- **F-027 (Medium) - `unlinkOAuthProviderForUser()` TOCTOU race, self-lockout:** the "don't remove the last sign-in method" guard (`userHasPasswordSet()` + `countLinkedOAuthProvidersForUser() <= 1`) and the `DELETE` that followed it were two independent statements with no serialisation between them. Two GENUINELY CONCURRENT unlinks of two DIFFERENT providers on a password-less account could both read the guard as "2 linked, passes" before either `DELETE` landed, both succeed, and leave the account with **zero sign-in credentials** - a permanent self-lockout with no recovery path.
  - **`_functions/fn_oauth.php`** - added `acquireOAuthUnlinkLock(int $userID): bool` / `releaseOAuthUnlinkLock(int $userID): void`, a per-user MySQL SESSION advisory lock (`GET_LOCK('cuercode_oauth_unlink:<userID>', 5)` / `RELEASE_LOCK(...)`) - the SAME mechanism as `fn_api_qrcodes.php`'s F-023 save-limit-lock fix, under its OWN lock namespace (`cuercode_oauth_unlink:`, distinct from F-023's `cuercode_save:`) so an in-flight `/save` and an in-flight unlink for the same user never contend with each other. `unlinkOAuthProviderForUser()` now acquires the lock FIRST, runs the guard-check + `DELETE` inside a `try` block, and releases the lock inside a `finally` covering every `return` path (a plain `return` triggers PHP's `finally`, unlike `exit()` - and nothing in this function ever calls `exit()`/`header()`, so no "outcome variable + release-after-the-fact" indirection was needed, unlike the F-023 fix which had to work around `errorResponse()`/`successResponse()`'s internal `exit()`). A `GET_LOCK()` timeout/error fails SAFE - the unlink is refused with a "busy, try again shortly" message rather than proceeding unserialised.
  - **Before/after concurrency proof (throwaway scratch MySQL, dropped after use; no credentials file ever written - constants defined inline in a scratch CLI driver script; genuinely concurrent OS `php` CLI processes, busy-wait-synchronised to a shared start instant - true parallelism, each its own MySQLi connection):** a password-less account with exactly 2 linked providers (`microsoft` + `google`). **BEFORE the fix** (the pre-fix code, `git show HEAD:.../fn_oauth.php`): 5/5 trials of a genuinely-concurrent double-unlink (two DIFFERENT `oauthID`s at once) both returned `success: true`; a direct DB check confirmed **0 linked providers + `passwordHash` still NULL** every single trial - the exact self-lockout the finding describes, reproduced MORE reliably than the review's own 2/15 (the busy-wait synchronisation tightens the race window considerably). **AFTER the fix**: the identical 5/5 trials each produced exactly ONE `success: true` + ONE `success: false` ("You cannot remove your only sign-in method...") - a direct DB check confirmed **exactly 1 linked provider** every single trial; the cap now HOLDS under genuine concurrency. A dedicated fail-safe probe (a separate MySQL session manually holding `cuercode_oauth_unlink:<userID>` for 8s) confirmed a genuine `GET_LOCK()` timeout correctly waits the full 5s `CUERCODE_OAUTH_UNLINK_LOCK_TIMEOUT_SECONDS` and then fails safe with the busy message (measured elapsed ~5.3s), touching zero rows.
- **F-028 (Low) - fail-OPEN CSRF helper:** `public_html/account/index.php`'s `accountPagePostCsrfValid()` returned `true` (CSRF check "passed") when `validateCSRFToken()` was undefined - a fail-OPEN default that, had `fn_csrf.php` somehow failed to load, would have waved through EVERY state-changing no-JS action on the account dashboard with no CSRF check at all. Fixed to fail CLOSED (`if (!function_exists('validateCSRFToken')) { return false; }`), matching `public_html/auth/index.php`'s own equivalent gate, which already failed closed.
- **F-029 (Low) - JWK `kty` not validated as RSA:** `oauthVerifyJwtSignatureRS256()` treated any JWK's `n`/`e` members as an RSA modulus/exponent pair without first checking `kty === 'RSA'`. Fixed - a JWK with `kty` missing, or set to anything other than the string `"RSA"` (e.g. `"EC"`, `"oct"` - a raw HMAC secret, never valid RSA key material), is now rejected with the same generic `ID_TOKEN_KEY_NOT_FOUND` used for "no matching key," BEFORE `n`/`e` are read at all. Defense-in-depth against a mixed/compromised (admin-configured) JWKS.
- **F-030 (Low) - multi-value `aud` without an `azp` check:** per OIDC Core §3.1.3.7 points 4-5, `oauthValidateIdTokenClaims()` now REQUIRES an `azp` (Authorized Party) claim, equal to this app's client_id, whenever `aud` is an array with MORE THAN ONE value - rejected with `ID_TOKEN_INVALID_AUDIENCE` otherwise. A single-string `aud` is unaffected (no `azp` requirement for the common case).
- **F-031 (Low) - CR/LF not explicitly stripped:** `resolveSafeSameSiteRedirect()` now runs `preg_match('/[\x00-\x1F\x7F]/', $rawNext)` FIRST, rejecting (falling back to the safe default) any value containing a CR, LF, or other ASCII control character - independent of whether a `:` co-occurs. Currently non-exploitable via this codebase's two callers (both feed the return value straight into `header('Location: ' . ...)`, and PHP's own `header()` has dropped newline-bearing values since 5.1.2), but that protection lives in a DIFFERENT layer - this closes the gap in the function itself as defence in depth for any future caller.

### Security / Fixed - SVG Logo Screening Parity on the Base64 API Path (2026-07-10, #52, F-024)

Closes the companion gap F-024 flagged (and left "queue"d, out of scope at the time) in its own CSP-hardening pass: the multipart `$_FILES` logo-upload path screened SVG content for active/script vectors before accepting it, but the JSON API's base64 `data:image/svg+xml;base64,...` logo path enforced ONLY the F-005 size/pixel caps - an unscreened malicious SVG logo could reach the generated QR's own SVG output verbatim via `overlayLogoOnSVG()` (which embeds the logo's raw bytes as a nested `<image href="data:image/svg+xml;base64,...">`). Chose **screening-with-parity** over a blanket SVG ban, so SVG logos remain usable via the API.

- **`_functions/fn_validation.php`** - extracted the dangerous-pattern SVG check previously hard-coded inline inside `validateImageUpload()` into a new SHARED, pure, unit-testable helper: **`screenSvgLogoContent(string $svgContent): array`**. `validateImageUpload()`'s SVG branch now calls it instead of its own inline pattern loop (behaviour for legitimate SVGs unchanged). The rule set is a SUPERSET of the original 5 patterns (`<script`, `on*=`, `javascript:`, `data:`, `<foreignObject`) - it additionally screens `vbscript:` URIs, `<!DOCTYPE`/`<!ENTITY` declarations (XXE / "billion laughs"), CSS `@import`/`expression()`, SMIL `<animate>`/`<set>` elements retargeting an event-handler attribute via `attributeName="on..."` (bypasses a naive static `on*=` scan), and any `href`/`xlink:href` value that is not a same-document `#fragment` reference (blocks `<use>`/`<image>` pulling in externally-hosted content).
- **`_functions/fn_qr_logo.php`** - `saveBase64LogoToTemp()` now calls the SAME `screenSvgLogoContent()` immediately after the existing F-005 decoded-byte cap and BEFORE any disk I/O, so a rejected malicious SVG never touches the filesystem. Runs whenever the declared MIME sub-type is `svg+xml` OR the decoded bytes sniff as `<svg` regardless of declared MIME (a mislabelled sub-type cannot bypass the screen). Raster logos (PNG/JPG/GIF/WEBP) are completely unaffected. If `fn_validation.php` is somehow not loaded, the base64 path now FAILS CLOSED for SVG rather than silently accepting unscreened content. Two new pure helpers were added for the API layer: `screenBase64LogoDataUri(string $dataUri): ?string` (no-disk-I/O pre-check) and `rejectUnsafeBase64SvgLogo(array $customization): ?string` (checks both `customization['logo_data']` and `customization['logo']`, since a client may supply the data URI directly as either field).
- **`_functions/fn_api_generate.php`** (`handleGenerate()`, `handlePreview()`) and **`_functions/fn_api_qrcodes.php`** (the `PATCH /qrcodes/{uuid}` handler) - all three now call `rejectUnsafeBase64SvgLogo()` BEFORE `validateCustomization()` and return a distinct, actionable **`HTTP 422 LOGO_SVG_REJECTED`** when an unsafe SVG logo is supplied, instead of the request silently succeeding with the logo quietly dropped (the pre-existing behaviour when `saveBase64LogoToTemp()` alone returns `null`).
- **New test file `tests/test_qr_logo.php`** (48 new assertions) - proves: `screenSvgLogoContent()` accepts a clean SVG and independently rejects each of the 13 vectors above (one isolated fixture per vector); `saveBase64LogoToTemp()` now rejects a malicious base64 SVG logo (confirmed no temp file is written) while still accepting a clean base64 SVG (byte-for-byte round-trip verified) and an unrelated genuine raster (PNG) logo unchanged; `screenBase64LogoDataUri()`/`rejectUnsafeBase64SvgLogo()` correctly flag a malicious logo via either `logo_data` or `logo`; and static regression guards pin that both intake paths call the SAME shared helper and that all three API call sites are wired to `LOGO_SVG_REJECTED`/422 BEFORE `validateCustomization()`.
- **Verified**: `php -l` clean on all 4 changed production files. `php tests/run.php`: **910/910 assertions green** (was 862/862 - **+48 new**, zero regressions).

### Security / Fixed - Sandbox Inline SVG Serving with CSP on qr-preview + Download (2026-07-10, #52, F-024)

Small, focused defence-in-depth hardening. Public saved QR codes are viewable cross-user, and `public_html/account/qr-preview/index.php` streams a saved code's SVG file `Content-Disposition: inline` as `image/svg+xml` for the account library's `<img>` thumbnail — meaning any SVG that ever slipped past the logo-upload screening could execute script in an inline view (stored-XSS on a public code). SECURITY.md F-024 has the full write-up; summary below.

- **`public_html/account/qr-preview/index.php`** - the inline (non-`?download=1`) branch now emits `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; sandbox` whenever the response is `image/svg+xml`. The `sandbox` directive (no allow-tokens) blocks script execution, forms, popups, and top-navigation while the image itself still renders. PNG/JPG/GIF/WEBP/PDF are untouched - they are inert and get no CSP.
- **`_functions/fn_api_download.php`** - audited `handleDownload()` (`GET /api/v1/download/{uuid}`): it ALWAYS sets `Content-Disposition: attachment` for every format including SVG - there is no inline-serving code path in this handler, so no CSP change was needed. A confirming comment now documents this so a future inline-preview addition doesn't silently reopen the gap.
- **`public_html/account/avatar/index.php`** - reviewed, left as-is (its extension map excludes `svg`, falling through to `application/octet-stream`, which browsers download rather than render); a one-line comment now pins this deliberate difference.
- **Verified live**: scratch local MySQL DB + `php -S`, both created and torn down for this check (no credentials file left on disk) - `GET qr-preview/?uuid=...` (inline) returns the CSP header above; the same UUID with `&download=1` does not, and returns `Content-Disposition: attachment` instead. `php -l` clean on all 3 touched files. `php tests/run.php`: **862/862 assertions green** (unaffected by this change - no test coverage gap introduced or claimed).
- **Companion audit finding, NOT fixed in this pass (flagged for owner triage, see F-024 for the full analysis)**: `fn_qr_logo.php`'s `overlayLogoOnSVG()` embeds a logo's RAW file bytes (base64'd into a nested `<image href="data:image/svg+xml;base64,...">`) into SVG-format QR output - it is not rasterised. The multipart file-upload logo intake path is screened for dangerous SVG content (`fn_validation.php` `validateImageUpload()`), but the JSON API's base64 `customization.logo_data` intake path (`fn_qr_logo.php` `saveBase64LogoToTemp()`) is NOT - it only enforces the F-005 size/pixel caps. This means a raw, unscreened SVG logo can reach the SVG QR output via that one specific path - a genuine, not purely theoretical, gap in the "primary control" this CSP hardening treats as authoritative. Recommended follow-up (out of scope here): apply the same dangerous-pattern screen (or a proper sanitiser) inside `saveBase64LogoToTemp()` for the `svg` case.

### Security / Fixed - Close saved_codes TOCTOU Race — Per-User Advisory Lock on Save-Limit Check+Claim (2026-07-10, #52/#53, F-023)

An independent IDOR/concurrency review of the saved-codes API (Epic E3 stage 2a, see the "Added" entry immediately below) found one HIGH finding: `POST /save`'s `saved_codes` plan-limit enforcement was a non-atomic check-then-act (TOCTOU) race. `web/CueRCode.net/_functions/fn_api_qrcodes.php` and `tests/test_qrcodes.php` changed; `openapi.json` gained a `SAVE_LOCK_BUSY` error code + a `429` example on `/save`.

- **F-023 (High, FIXED) - `saved_codes` plan-limit TOCTOU race**: `handleSaveQRCode()`'s live `COUNT(*)` check against the caller's plan limit and the claim `UPDATE` that followed it were two independent statements with no serialisation between them. N truly-concurrent `POST /save` requests for N DIFFERENT unclaimed UUIDs from the SAME user could each pass the count check before any claim landed, blowing straight past the account's plan cap - well within the existing per-key rate limit, so rate limiting alone did not mitigate it. The pre-existing `UPDATE ... WHERE (userID IS NULL OR userID = ?)` guard only ever stopped two requests racing for the SAME `qrID` - it did nothing when the `qrID`s differed, which is exactly what the exploit used.
- **Fix - per-user MySQL advisory lock, not a transaction + `SELECT ... FOR UPDATE`**: the count-check and the claim `UPDATE` are now serialised, per caller, by a MySQL SESSION advisory lock - `acquireSaveLimitLock()`/`releaseSaveLimitLock()` (new), wrapping `SELECT GET_LOCK('cuercode_save:<userID>', 5)` / `SELECT RELEASE_LOCK(...)`. A transaction + `SELECT ... FOR UPDATE` would NOT have closed this gap: the code being claimed is, at SELECT time, owned by NOBODY (`userID IS NULL`), so there is no row yet "belonging" to this user's future claim for row-level locking to lock against - a phantom-row problem. `GET_LOCK()`/`RELEASE_LOCK()` are connection-scoped in MySQL, and `getDB()` (`_includes/db_connect.php`) is a per-request cached-connection singleton, so the lock, the count-check, and the claim `UPDATE` all run on the SAME `mysqli` connection by construction - confirmed by code inspection, not merely assumed. A `GET_LOCK()` timeout or error (0/NULL) FAILS SAFE: the request is rejected with `429 SAVE_LOCK_BUSY` + a `Retry-After` header rather than proceeding unserialised, which would silently reopen the exact race the fix exists to close. The lock is released inside a `finally` block covering EVERY exit path - normal completion, any caught exception, and a belt-and-braces outer catch - never skipped. This required restructuring `handleSaveQRCode()`'s critical section to populate an `$outcome` descriptor rather than calling `errorResponse()`/`successResponse()` directly: both of those functions call `exit()` internally, and a standalone PHP repro run this session confirmed PHP's `finally` block does NOT execute past an `exit()` call (only a normal `return` or a thrown exception triggers it) - so neither function may run from inside the locked section, or the lock could be left held on that path. Only a genuinely NEW claim acquires the lock; an already-owned code being re-saved has no plan-limit check to race, so that path is unaffected.
- **RE-PROOF - live scratch-DB + MULTIPLE independent `php -S` OS processes (true parallelism)**: reproduced the reviewer's exact setup - a throwaway scratch MySQL database (dropped after use; DB/encryption credentials defined as PHP constants via a `php -S` `auto_prepend_file`, never written to a credentials file), the REAL router (`public_html/api/v1/index.php`) served by 5-8 INDEPENDENT `php -S` processes (a single dev-server instance serialises requests and would have falsely looked safe - PHP's built-in server does not handle concurrent requests within one process), and a plan-capped (`saved_codes: 2`) test account. **BEFORE the fix** (the pre-fix code checked out from `git show HEAD` into a separate scratch tree): 5 truly-concurrent `POST /save` calls for 5 DIFFERENT unclaimed UUIDs all returned `201` - a direct DB count confirmed **5 saved codes for a cap-2 account** (2.5x over cap). **AFTER the fix**: the identical 5-way burst against the SAME cap-2 user produced exactly **2×`201` + 3×`402 SAVED_CODES_LIMIT_REACHED`** - a direct DB count confirmed **exactly 2** saved codes; an 8-way burst (8 independent OS processes) reproduced the identical result (2/8 succeeded, DB count 2). A dedicated fail-safe probe manually held the per-user lock from a SEPARATE MySQL session for 8 seconds and confirmed a genuine `GET_LOCK()` timeout correctly returned `429 SAVE_LOCK_BUSY` with `Retry-After: 2` after waiting the full 5-second timeout, touching zero database rows. Serial save→delete→save (a soft-deleted code frees a slot, and the freed slot is genuinely reusable) and the `-1` (unlimited, `business` plan) case were both re-verified working correctly and unaffected by the fix (3/3 concurrent saves succeeded for the unlimited-plan account, no cap applied). Scratch database and all `php -S` processes were torn down after use.
- **Tests**: `tests/test_qrcodes.php` gained 20 new static, source-text regression-guard assertions (Section 8) - a genuine concurrent race cannot be asserted in this dependency-free, single-process, no-DB harness (same limitation this file's docblock already documents for every other DB-touching handler), so this instead pins: `acquireSaveLimitLock()`/`releaseSaveLimitLock()`'s exact signatures, that the lock is a real `GET_LOCK()`/`RELEASE_LOCK()` call (not a stub), that it is scoped PER-USER (not per-qrID or global - the property that actually closes the race), and - the critical invariant - that no `errorResponse()`/`successResponse()` call exists between acquiring and releasing the lock in `handleSaveQRCode()`. Full suite: **834/834 assertions green** (was 814/814 - +20 new).
- **Verification**: `php -l` clean on all changed/new files; `openapi.json` re-validated as well-formed JSON (16 paths, unchanged) with a new `SAVE_LOCK_BUSY` error code documented and a `save_lock_busy` example added to `/save`'s `429` response (alongside the pre-existing router-level `RATE_LIMIT_EXCEEDED` example, since both now share that status code on this endpoint).
- **Not touched**: no schema change (the lower-blast-radius advisory-lock approach was chosen over the alternative atomic-counter-column design the task offered, specifically to avoid a schema migration and a drift-prone counter that would need decrement-on-soft-delete bookkeeping). GitHub issues were not touched, per this task's explicit "do not touch GitHub issues" instruction.

### Security / Fixed - Independent Auth Security Review: Register Timing Side-Channel, Error-Log PII, Session-ID Masking (2026-07-10, #52, E3 stage 1)

An independent security review of the just-shipped Epic E3 stage 1 auth engine (see the entry immediately below) found one High and two Low findings, plus one dead-code item, all fixed in this pass. `web/CueRCode.net/_functions/fn_auth.php`, `web/CueRCode.net/_functions/fn_error_handler.php`, `web/CueRCode.net/_functions/fn_api_accounts.php`, `web/CueRCode.net/_functions/fn_api_auth.php`, and `tests/test_auth.php` changed.

- **F-021 (High) - `registerUser()` response-timing side-channel (email enumeration)**: the "email already exists" branch returned immediately after a sub-millisecond indexed SELECT, while ONLY the "new email" branch ran `hashPassword()` (Argon2id, ~80-90ms at the F-013 cost parameters, 64 MiB / 4 iterations / 2 threads) - an easily-automatable, real-HTTP-measurable timing gap let an attacker enumerate registered emails even though the response BODY was already identical between the two branches (the F-013/E3-stage-1 anti-enumeration design's intent was defeated by TIMING alone). Fixed in `fn_auth.php` `registerUser()`: `hashPassword()` now runs UNCONDITIONALLY, before the existence-check SELECT, and the pre-computed hash is reused for the INSERT on the "new email" path - both branches now pay the identical Argon2id cost before either can return. **Live scratch-DB measurement** (throwaway local MySQL 9.6, dropped after use, credentials pre-defined as PHP constants - no credentials file ever written to disk): loaded the REAL `fn_password.php`/`fn_auth.php`/`db_connect.php` against the scratch DB and timed 40-60 trials per branch, twice independently. BEFORE: existing-email mean 0.42-0.59ms vs. new-email mean 81.6-89.7ms (gap **81-89ms**, effect size **9.75x-39.4x** pooled stdev). AFTER: existing-email mean 79.7-88.7ms vs. new-email mean 82.4-89.1ms (gap **0.46-2.68ms**, effect size **0.02x-0.79x** pooled stdev) - the gap collapsed from a trivially-observable 10-40-stdev signal to sub-1-stdev noise. Closes SECURITY.md F-021 (new finding, marked FIXED).
- **Finding 2 (Low) - PII in error log on duplicate-registration race**: the same function's INSERT-catch block previously logged the caught exception's `getMessage()` verbatim via `logError()`; for a MySQL unique-constraint violation on `tblUsers.email` that message is literally `"Duplicate entry '<email>' for key ..."`, putting the plaintext registrant email into `tblErrorLog`. Fixed by classifying the duplicate-key case (`\mysqli_sql_exception` with MySQL errno 1062, or a wrapped `RuntimeException` embedding the same "Duplicate entry" wording) and logging a GENERIC title/detail ("Registration insert conflict (duplicate email)") instead - never the raw driver text for this specific failure mode; any other, non-duplicate-key insert failure still logs its real message. **Verified with a genuine concurrent race**: two real child PHP processes, busy-wait-synchronised to a shared target timestamp via `proc_open`, both called the production `registerUser()` for the identical brand-new email - 5/5 attempts produced exactly one `tblUsers` row and zero PII in `tblErrorLog` (only the new generic wording). A direct probe of the identical INSERT statement (pre-existing the row, then re-running the exact same query) independently confirmed the raw driver message DOES contain the plaintext email (`mysqli_sql_exception`, code 1062, `"Duplicate entry '<email>' for key 'tblusers.idx_user_email'"`), proving both the pre-fix exposure and the fix's effectiveness. Amends SECURITY.md F-008.
- **Finding 3 (Low, defense-in-depth) - session id in `tblErrorLog`**: `fn_error_handler.php`'s `logError()` previously stored the raw `session_id()` return value verbatim in the `sessionID` column - `tblErrorLog` is a lower-privilege, longer-retention audit table than the session store itself, so this was a broader exposure than the footer's own session-id display (SECURITY.md F-019, already masked to last-8-chars for DISPLAY). Fixed by storing `substr(hash('sha256', $rawSessionID), 0, 16)` instead - never any raw characters, since this is AT-REST storage rather than a same-session view. **Verified live**: started a real PHP session with a known raw id, forced an error through the production `logError()`, and confirmed the resulting `tblErrorLog` row's `sessionID` column equals the expected masked hash exactly (not the raw id, not any substring of it). Amends SECURITY.md F-019.
- **Cleanup (Low) - dead code**: removed the unreachable `$_POST['csrf_token']` fallback from both `requireCsrfOrApiKey()` (`fn_api_accounts.php`) and `authenticateAPIRequest()` (`fn_api_auth.php`). The router (`public_html/api/v1/index.php`) mandates `Content-Type: application/json` on every non-empty POST body and rejects anything else with 415 BEFORE either function runs (F-009); PHP only auto-populates `$_POST` for `application/x-www-form-urlencoded`/`multipart/form-data` bodies, so a genuine form POST can never reach either function with a populated `$_POST`. Replaced with an explanatory comment in both files rather than silently deleting the historical context. The existing 403-vs-401 status-code convention was intentionally left unchanged (deferred to a later, deliberate pass per this review's scope).
- **Regression coverage**: added a new Section 7 to `tests/test_auth.php` (13 new assertions, static source-text checks, no DB/execution) that pins: `hashPassword()` is called before the existence-check SELECT in `registerUser()` (F-021 guard); the pre-fix unconditional-raw-message `logError()` call is gone and the new `mysqli_sql_exception`/generic-title classification is present (Finding 2 guard); the pre-fix raw `$sessionID = session_id();` assignment is gone and the masked-hash form is present (Finding 3 guard); and the `isset($_POST['csrf_token'])` read is gone from both `fn_api_accounts.php` and `fn_api_auth.php` (cleanup guard). Full suite: **703/703 assertions green** (690 pre-existing + 13 new). `php -l` clean on all four changed production files plus `tests/test_auth.php`.
