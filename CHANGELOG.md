### Security / Fixed - Close saved_codes TOCTOU Race — Per-User Advisory Lock on Save-Limit Check+Claim (2026-07-10, #52/#53, F-023)

An independent IDOR/concurrency review of the saved-codes API (Epic E3 stage 2a, see the "Added" entry immediately below) found one HIGH finding: `POST /save`'s `saved_codes` plan-limit enforcement was a non-atomic check-then-act (TOCTOU) race. `web/CueRCode.net/_functions/fn_api_qrcodes.php` and `tests/test_qrcodes.php` changed; `openapi.json` gained a `SAVE_LOCK_BUSY` error code + a `429` example on `/save`.

- **F-023 (High, FIXED) - `saved_codes` plan-limit TOCTOU race**: `handleSaveQRCode()`'s live `COUNT(*)` check against the caller's plan limit and the claim `UPDATE` that followed it were two independent statements with no serialisation between them. N truly-concurrent `POST /save` requests for N DIFFERENT unclaimed UUIDs from the SAME user could each pass the count check before any claim landed, blowing straight past the account's plan cap - well within the existing per-key rate limit, so rate limiting alone did not mitigate it. The pre-existing `UPDATE ... WHERE (userID IS NULL OR userID = ?)` guard only ever stopped two requests racing for the SAME `qrID` - it did nothing when the `qrID`s differed, which is exactly what the exploit used.
- **Fix - per-user MySQL advisory lock, not a transaction + `SELECT ... FOR UPDATE`**: the count-check and the claim `UPDATE` are now serialised, per caller, by a MySQL SESSION advisory lock - `acquireSaveLimitLock()`/`releaseSaveLimitLock()` (new), wrapping `SELECT GET_LOCK('cuercode_save:<userID>', 5)` / `SELECT RELEASE_LOCK(...)`. A transaction + `SELECT ... FOR UPDATE` would NOT have closed this gap: the code being claimed is, at SELECT time, owned by NOBODY (`userID IS NULL`), so there is no row yet "belonging" to this user's future claim for row-level locking to lock against - a phantom-row problem. `GET_LOCK()`/`RELEASE_LOCK()` are connection-scoped in MySQL, and `getDB()` (`_includes/db_connect.php`) is a per-request cached-connection singleton, so the lock, the count-check, and the claim `UPDATE` all run on the SAME `mysqli` connection by construction - confirmed by code inspection, not merely assumed. A `GET_LOCK()` timeout or error (0/NULL) FAILS SAFE: the request is rejected with `429 SAVE_LOCK_BUSY` + a `Retry-After` header rather than proceeding unserialised, which would silently reopen the exact race the fix exists to close. The lock is released inside a `finally` block covering EVERY exit path - normal completion, any caught exception, and a belt-and-braces outer catch - never skipped. This required restructuring `handleSaveQRCode()`'s critical section to populate an `$outcome` descriptor rather than calling `errorResponse()`/`successResponse()` directly: both of those functions call `exit()` internally, and a standalone PHP repro run this session confirmed PHP's `finally` block does NOT execute past an `exit()` call (only a normal `return` or a thrown exception triggers it) - so neither function may run from inside the locked section, or the lock could be left held on that path. Only a genuinely NEW claim acquires the lock; an already-owned code being re-saved has no plan-limit check to race, so that path is unaffected.
- **RE-PROOF - live scratch-DB + MULTIPLE independent `php -S` OS processes (true parallelism)**: reproduced the reviewer's exact setup - a throwaway scratch MySQL database (dropped after use; DB/encryption credentials defined as PHP constants via a `php -S` `auto_prepend_file`, never written to a credentials file), the REAL router (`public_html/api/v1/index.php`) served by 5-8 INDEPENDENT `php -S` processes (a single dev-server instance serialises requests and would have falsely looked safe - PHP's built-in server does not handle concurrent requests within one process), and a plan-capped (`saved_codes: 2`) test account. **BEFORE the fix** (the pre-fix code checked out from `git show HEAD` into a separate scratch tree): 5 truly-concurrent `POST /save` calls for 5 DIFFERENT unclaimed UUIDs all returned `201` - a direct DB count confirmed **5 saved codes for a cap-2 account** (2.5x over cap). **AFTER the fix**: the identical 5-way burst against the SAME cap-2 user produced exactly **2×`201` + 3×`402 SAVED_CODES_LIMIT_REACHED`** - a direct DB count confirmed **exactly 2** saved codes; an 8-way burst (8 independent OS processes) reproduced the identical result (2/8 succeeded, DB count 2). A dedicated fail-safe probe manually held the per-user lock from a SEPARATE MySQL session for 8 seconds and confirmed a genuine `GET_LOCK()` timeout correctly returned `429 SAVE_LOCK_BUSY` with `Retry-After: 2` after waiting the full 5-second timeout, touching zero database rows. Serial save→delete→save (a soft-deleted code frees a slot, and the freed slot is genuinely reusable) and the `-1` (unlimited, `business` plan) case were both re-verified working correctly and unaffected by the fix (3/3 concurrent saves succeeded for the unlimited-plan account, no cap applied). Scratch database and all `php -S` processes were torn down after use.
- **Tests**: `tests/test_qrcodes.php` gained 20 new static, source-text regression-guard assertions (Section 8) - a genuine concurrent race cannot be asserted in this dependency-free, single-process, no-DB harness (same limitation this file's docblock already documents for every other DB-touching handler), so this instead pins: `acquireSaveLimitLock()`/`releaseSaveLimitLock()`'s exact signatures, that the lock is a real `GET_LOCK()`/`RELEASE_LOCK()` call (not a stub), that it is scoped PER-USER (not per-qrID or global - the property that actually closes the race), and - the critical invariant - that no `errorResponse()`/`successResponse()` call exists between acquiring and releasing the lock in `handleSaveQRCode()`. Full suite: **834/834 assertions green** (was 814/814 - +20 new).
- **Verification**: `php -l` clean on all changed/new files; `openapi.json` re-validated as well-formed JSON (16 paths, unchanged) with a new `SAVE_LOCK_BUSY` error code documented and a `save_lock_busy` example added to `/save`'s `429` response (alongside the pre-existing router-level `RATE_LIMIT_EXCEEDED` example, since both now share that status code on this endpoint).
- **Not touched**: no schema change (the lower-blast-radius advisory-lock approach was chosen over the alternative atomic-counter-column design the task offered, specifically to avoid a schema migration and a drift-prone counter that would need decrement-on-soft-delete bookkeeping). GitHub issues were not touched, per this task's explicit "do not touch GitHub issues" instruction.
- **Commits**: made directly on `launch-prep/2026-07-10` (same branch as the prior #47/#48/#49/#50/#29/#52/#53 sessions). Work is commit-only per the task directive; the conductor pushes.

### Added - Saved-Codes API: /save + /qrcodes CRUD with Ownership/IDOR Enforcement + Plan Limits (2026-07-10, #52/#24, Epic E3 stage 2a)

Implements PROJECT_ROADMAP.md **Epic E3 stage 4** ("API: /save, GET/PATCH/DELETE /qrcodes — with ownership checks + IDOR test pack") - the app's **first ownership-scoped resource surface**. Everything a user can save/list/edit/delete now goes through re-derived, per-request ownership checks against the caller's server-side session/API-key identity; no client-supplied identifier is ever trusted. **Deliberately deferred this stage** (per the parent epic's staging): account UI pages (stage 5), self-service API-key management UI (needs E6, gated on E3), organisations (stage 6), admin dashboard (stage 8), GDPR export/erasure (#37).

- **Schema (`install.sql`, `tblQRCodes`):** two new columns - `qrLabel VARCHAR(150) NULL` (caller-supplied nickname) and `deletedAt DATETIME NULL` (soft-delete marker) - plus a new composite index `idx_qr_user_active (userID, deletedAt)`. Every saved-codes query in the new code filters `deletedAt IS NULL`, so a deleted row disappears from list/get/patch/delete/download AND stops counting against the caller's `saved_codes` plan limit, while remaining on disk/in the DB for audit purposes (see the soft-delete design decision below). `isPublic` (already existed, previously unused) is now load-bearing.
- **`_functions/fn_api_qrcodes.php` (new)** - the saved-codes engine + HTTP handlers:
  - **`POST /api/v1/save`** (`handleSaveQRCode()`) - claims a previously-generated code (by `uuid`) into the caller's account, or updates label/visibility if already owned. Enforces `limitFor('saved_codes', $userID)` (-1 = unlimited; seeded `anonymous=0/free=25/pro=500/business=-1`) via a live `COUNT(*) WHERE userID=? AND deletedAt IS NULL` check, ONLY for a genuinely new claim (re-saving an already-owned code never consumes a slot) - over-cap returns `402 SAVED_CODES_LIMIT_REACHED` with `upgrade_url`+`plan_limit`. A code already claimed by a DIFFERENT user is reported as `404` (never `409`/`403`) - blocks claim-hijacking without disclosing the UUID belongs to somebody else. The atomic `UPDATE ... WHERE qrID = ? AND (userID IS NULL OR userID = ?)` plus a post-update re-SELECT close the two-concurrent-claims race.
  - **`GET /api/v1/qrcodes`** (`handleListQRCodes()`) - lists ONLY `WHERE userID = ?` (never widened to public/other-user rows), paginated (`page`/`per_page`, capped at 100 via `clampPaginationParams()`), optional `type` filter.
  - **`GET/PATCH/DELETE /api/v1/qrcodes/{uuid}`** - one router entry (the router matches by pattern, not pattern+method; see below), dispatched by `handleQrCodeItem()` reading `$_SERVER['REQUEST_METHOD']`. GET allowed if owner OR `isPublic`; PATCH/DELETE require TRUE ownership (`isPublic` never grants write) - all three re-fetch the row (`fetchQrCodeRowByUuid()`) and check ownership FRESH, every request, before any read/mutate/delete. Not-owned-and-not-public → `404` (never `403`), everywhere.
  - **PATCH regeneration**: when `customization` is supplied, the merged (stored ∪ patch) customisation is validated (`buildCustomizationFromRequest()`/`validateCustomization()`/`applyAccessiblePreset()` - same functions `/generate` uses) and the image is re-rendered in place from the code's EXISTING payload (`regenerateQrOutputForPatch()`, mirroring `generateQRCode()`'s render/logo/frame steps) - the `uuid`/`download_url` never change. `qrOptions`/`qrOutputFormat`/`qrFilePath`/`qrFileSize` are updated; a stale file at the old path (format change) is cleaned up best-effort. Scope trim: the E5/#49 accessible/tactile/Avery PDF composition step is NOT re-applied on PATCH (documented in the function's own docblock) - use `/generate`+`/save` for those layouts.
  - **The three ownership predicates - `qrCodeIsReadableBy()`/`qrCodeIsWritableBy()`/`qrCodeIsDownloadableBy()`** - are the ENTIRE access-control decision surface for this stage: every route (including the hardened `/download/{uuid}` below) calls exactly one of them, so there is a single, auditable, unit-tested source of truth rather than five inline ownership checks that could drift. `qrCodeIsDownloadableBy()` deliberately treats an UNCLAIMED code (`userID IS NULL` - never passed through `/save`) as downloadable by any authenticated caller, preserving the pre-existing anonymous generate→download flow (nobody's saved-library privacy is at stake for a code nobody has claimed).
- **`_functions/fn_api_download.php` - ownership hardening (ADDRESSES THE PRE-EXISTING GAP flagged in SECURITY.md's E3 stage 1 coverage row: "IDOR audit still owed once the next stage ships ownership-scoped routes"):** `handleDownload()` now takes the router's `$auth` context and, for a code that HAS been claimed (`userID IS NOT NULL`), only serves it to the owner or when `isPublic=1` - otherwise `404` (identical to an unknown UUID, never `403`). An unclaimed code is unaffected (still downloadable by any authenticated caller, as before this stage - see `qrCodeIsDownloadableBy()` above). The route's own `auth => true` router-level requirement is UNCHANGED.
- **Router (`public_html/api/v1/index.php`):** three new route-table entries (`save` POST, `qrcodes` GET, `qrcodes/{uuid}` GET+PATCH+DELETE - all `auth => true`, `rateLimit => true`), `fn_api_qrcodes.php` added to the loader list, `Access-Control-Allow-Methods` extended to include `PATCH, DELETE` (was `GET, POST, OPTIONS` only - the same static header in `public_html/api/v1/.htaccess` updated too, so Apache's `mod_headers` directive can't silently override the PHP-emitted value with a stale list).
- **OpenAPI 3.0.3** (`openapi.json`): 3 new paths (`/save`, `/qrcodes`, `/qrcodes/{uuid}` - 16 total, was 13), a new `Saved Codes` tag, 9 new schemas (`SaveRequest`/`SaveResponse`/`QrCodeSummary`/`QrCodeListResponse`/`QrCodeDetailResponse`/`PatchQrCodeRequest`/`PatchQrCodeResponse`), a new reusable `PaymentRequired` (402) response component, and an extended `ErrorResponse.error_code` catalogue (`INVALID_UUID`, `INVALID_LABEL`, `NO_FIELDS`, `SAVED_CODES_LIMIT_REACHED`, `SAVE_CONFLICT`, `SAVE_FAILED`, `LIST_FAILED`, `UPDATE_FAILED`, `DELETE_FAILED`, `REGENERATION_FAILED`, `FILE_SAVE_FAILED`, `ACCESSIBLE_CONTRAST_TOO_LOW`).
- **Owner/design decisions made this stage (see DEV_NOTES.md for the full rationale):**
  - **Soft delete** (`deletedAt`), not hard delete - matches this codebase's existing reversible-state convention (`tblUserSessions.revokedAt`, `tblEmailVerifications`/`tblPasswordResets.usedAt`); preserves an audit trail and a future undo path at the accepted cost of the row/file persisting until a later retention job (not built this stage) reaps it.

- **Tests (`tests/test_qrcodes.php`, new, 63 assertions, no-DB harness):** exhaustive truth-table coverage of all three ownership predicates (the entire IDOR-enforcement surface, independent of the live pack below), `isValidQrUuid()` (incl. a SQL-injection-shaped rejection case), `validateQrLabelInput()` (absent-vs-explicit-null distinction, trim/blank-clears, exact-length-boundary, multi-byte/emoji character counting, non-string rejection), `sanitizeQrTypeFilter()`, and `clampPaginationParams()` (zero/negative/non-numeric/over-cap inputs). `tests/test_openapi_render.php` updated for the 16-path spec. Full suite: **814/814 assertions green** (751 pre-existing + 63 new; the pre-existing count also includes 3 new `test_openapi_render.php` path-list assertions from this stage).
- **Scratch-DB + live-HTTP IDOR pack this session (throwaway local MySQL, dropped after use; scratch credentials as PHP constants only - no credentials file ever written to disk):** installed `install.sql`+`seed_data.sql` (0 errors, confirming the new `qrLabel`/`deletedAt` columns + index), provisioned 3 real accounts (A, B, and a rate/limit-test account C with a synthetic `saved_codes: 2` plan via one SQL statement - zero code needed), started PHP's built-in server against the REAL router, and drove 32/32 checks with `curl` and `X-API-Key` auth:

### Security / Fixed - Independent Auth Security Review: Register Timing Side-Channel, Error-Log PII, Session-ID Masking (2026-07-10, #52, E3 stage 1)

An independent security review of the just-shipped Epic E3 stage 1 auth engine (see the entry immediately below) found one High and two Low findings, plus one dead-code item, all fixed in this pass. `web/CueRCode.net/_functions/fn_auth.php`, `web/CueRCode.net/_functions/fn_error_handler.php`, `web/CueRCode.net/_functions/fn_api_accounts.php`, `web/CueRCode.net/_functions/fn_api_auth.php`, and `tests/test_auth.php` changed.

- **F-021 (High) - `registerUser()` response-timing side-channel (email enumeration)**: the "email already exists" branch returned immediately after a sub-millisecond indexed SELECT, while ONLY the "new email" branch ran `hashPassword()` (Argon2id, ~80-90ms at the F-013 cost parameters, 64 MiB / 4 iterations / 2 threads) - an easily-automatable, real-HTTP-measurable timing gap let an attacker enumerate registered emails even though the response BODY was already identical between the two branches (the F-013/E3-stage-1 anti-enumeration design's intent was defeated by TIMING alone). Fixed in `fn_auth.php` `registerUser()`: `hashPassword()` now runs UNCONDITIONALLY, before the existence-check SELECT, and the pre-computed hash is reused for the INSERT on the "new email" path - both branches now pay the identical Argon2id cost before either can return. **Live scratch-DB measurement** (throwaway local MySQL 9.6, dropped after use, credentials pre-defined as PHP constants - no credentials file ever written to disk): loaded the REAL `fn_password.php`/`fn_auth.php`/`db_connect.php` against the scratch DB and timed 40-60 trials per branch, twice independently. - **Finding 2 (Low) - PII in error log on duplicate-registration race**: the same function's INSERT-catch block previously logged the caught exception's `getMessage()` verbatim via `logError()`; for a MySQL unique-constraint violation on `tblUsers.email` that message is literally `"Duplicate entry '<email>' for key ..."`, putting the plaintext registrant email into `tblErrorLog`. Amends SECURITY.md F-019.
