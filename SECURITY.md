# CueRCode — Security Register

> Phase-0 (dev-team-security) threat-modelling and adversarial PoC pass is complete. This register reflects the full Phase-0 audit across six surfaces with 6+ independent adversarial scouts, a cross-validator, and a documentarian. Findings are cross-referenced to PROJECT.md backlog IDs (B-###). IDs are stable and zero-padded.

## Attack surface

Phase-0 audited the following surfaces in depth. For each surface the trust boundary is noted and the audit scope is summarised.

### 1. REST API — auth, authorization & access control

**Files:** `public_html/api/v1/index.php`, `_functions/fn_api_auth.php`, `_functions/fn_api_download.php`
**Trust boundary:** The internet (anonymous callers) to authenticated generate/preview/download endpoints. Anonymous callers may only reach health, types, and formats. CSRF token (session-bound, `hash_equals`, 3600 s TTL) is required for web-UI generate/preview. API keys (HMAC-SHA256, `hash_equals`) are a Phase-2 feature — not yet wired.
**Audited:** Timing-safe comparison paths, anonymous-fallback scope, API-key validation and length checks, rate limiting logic end-to-end (schema vs code), trusted-proxy XFF gating, download UUID/path-traversal guard.
**PoC method:** Static analysis only — no live instance available.

### 2. REST API — input handling, payload size, CORS, Content-Type

**Files:** `public_html/api/v1/index.php`, `_functions/fn_api_generate.php`, `_functions/fn_response.php`, `public_html/api/v1/.htaccess`
**Trust boundary:** Raw HTTP request body (JSON) from untrusted callers.
**Audited:** `php://input` read with no Content-Type gate, per-field length caps, CORS `Access-Control-Allow-Origin` default and `.htaccess` hardcode, header-injection via CORS config value (rejected — PHP header() blocks CR/LF since 5.1.2).
**PoC method:** Static analysis; PHP version behaviour for header() confirmed from PHP changelog.

### 3. File handling — QR generation & download pipeline

**Files:** `_functions/fn_qr_generate.php`, `_functions/fn_qr_logo.php`, `_functions/fn_api_download.php`, `_functions/fn_validation.php`
**Trust boundary:** Authenticated caller supplying customization JSON (logo path/data URI) → GD/FPDF → stored file → streaming download.
**Audited:** tblQRCodes column names vs schema (install.sql), download UUID+realpath guard, base64 logo decoded-size and pixel-dimension limits, file-path logo case with realpath base-dir containment, predefined-logo DB lookup column names, SVG polyglot/MIME, GD loadLogoImage safety.
**PoC method:** Static analysis; schema cross-checked against install.sql line by line.

### 4. Cryptography, secrets & session management

**Files:** `_functions/fn_encryption.php`, `_functions/fn_csrf.php`, `_includes/bootstrap.php`, `public_html/install/index.php`
**Trust boundary:** Internally trusted code paths; secrets stored in `_auth_keys/` (never committed, `.htaccess` deny-all, `.gitignore`).
**Audited:** AES-256-GCM with HKDF, random IV per encryption, GCM auth-tag verification, CSRF token entropy and timing-safe compare, session-cookie flags, API-key length constant vs generated key length.
**PoC method:** PHP calculation (string lengths verified): `strlen('cuercode_') + strlen(bin2hex(random_bytes(20)))` = 9 + 40 = 49; constant = 45 → mismatch confirmed.

### 5. Output encoding & XSS — web UI, templates, JavaScript, error pages

**Files:** `public_html/index.php`, `_includes/header.php`, `_includes/footer.php`, `assets/js/cuercode-common.js`, `assets/js/cuercode-generator.js`, error pages
**Trust boundary:** Server-controlled HTML output and client-side DOM manipulation from API responses.
**Audited:** `htmlspecialchars(ENT_QUOTES,'UTF-8')` coverage in all PHP templates, `CueRCode.escapeHtml()` usage in JS form-field rendering, jQuery(toastHtml) sink in `notify()`, API response field names (`message` vs `error`), session ID echo in debug panel.
**PoC method:** Static analysis; traced API response field names from `fn_response.php:269-275` to `cuercode-generator.js:1126-1127`.

### 6. HTTP headers, transport, installer & directory protection

**Files:** `public_html/.htaccess`, `public_html/api/v1/.htaccess`, `_*/.htaccess` (6 deny-all files), `public_html/install/index.php`, `sw.js`, `robots.txt`, `_includes/cron/process_email_queue.php`
**Trust boundary:** Network perimeter (HTTP/HTTPS) → Apache → PHP.
**Audited:** HSTS, HTTP→HTTPS redirect, `session.cookie_secure` vs bootstrap dynamic detection, CSP `unsafe-inline`, SRI on CDN assets, CORS default in `.htaccess`, installer re-run protection via `.installed.lock`, `robots.txt` advertising `/install/`, directory deny-all coverage, service-worker scope, security headers (`X-Content-Type-Options`, `X-Frame-Options`, `X-XSS-Protection`, `Referrer-Policy`, `Permissions-Policy`); email queue runner refuses any non-command-line run (403) before loading anything; lives outside the web root under deny-all `_includes/`.
**PoC method:** Static analysis; `.htaccess` and `robots.txt` read directly.

### 7. SSO / OAuth2-OIDC client (Epic E2, #55/#19/#20/#28, 2026-07-10)

**Files:** `_functions/fn_oauth.php`, `public_html/auth/index.php`, `public_html/auth/callback/index.php`, `_includes/sql/seed_data.sql` (group `sso`), `public_html/.htaccess`
**Trust boundary:** THREE new boundaries at once — (a) the internet-facing callback route, which must treat an inbound `code`/`state` as fully untrusted even though it appears to originate from a trusted IdP redirect; (b) the IdP itself, whose `id_token` assertions (especially `email_verified`) must be cryptographically verified, never taken on faith; (c) the account-linking decision, which must not let a newly-observed external identity silently annex an EXISTING local account.
**Audited (self-review at build time, this stage):** PKCE (S256) + `state` + `nonce` generation and single-use consumption (`oauthConsumePendingState()` burns the pending attempt on read, success or failure); the open-redirect allowlist (`resolveSafeSameSiteRedirect()`); RS256-only `id_token` signature verification via hand-rolled JWK→PEM + `openssl_verify()` (explicit `alg: none`/`HS256` alg-confusion rejection); `iss`/`aud`/`exp`/`iat`/`nonce` claim validation; the account-linking decision table (`decideOAuthAccountLinkAction()`) for every branch, including the two takeover-adjacent ones (verified-email collision with an existing unlinked account → refuse; identity already linked to a different account → refuse); token-bundle-at-rest encryption (AES-256-GCM via the existing `encryptValue()`); the CSRF-token requirement on the authenticated "link a provider" initiation path; and the inert-by-default provider-registry gating (`ssoProviderIsUsable()`) that keeps the ENTIRE subsystem a no-op absent explicit owner configuration.
**PoC method:** Static analysis + a REAL in-process RS256 signature round-trip (`tests/test_oauth.php` — an actual `openssl_pkey_new()` keypair signs a genuine JWT, verified against a matching JWKS, with bad iss/aud/exp/nonce/signature/alg variants independently proven rejected) and the full decision-table truth table exercised as a pure function. **No live IdP round-trip performed** — no real Microsoft/Google/SIGNula app registration exists yet (by design — see the task's "no real IdP credentials, ever" constraint); the authorize→callback→session flow against a REAL IdP is deferred to the owner's first live configuration, at which point a scratch-DB + real-HTTP follow-up pass (matching every other Epic E3/E4/E7 stage's own verification convention) should be run and recorded here.

**Independent re-audit (E2, 2026-07-10, `launch-prep/2026-07-10`, #55) — concurrency + spec-conformance lens:** a follow-up review probed for what the self-review above did not — concurrent-request account-state races (found F-027, a TOCTOU race in `unlinkOAuthProviderForUser()`, fixed with the same per-user MySQL advisory-lock pattern as F-023) and stricter OIDC-spec/defence-in-depth conformance (found F-028 fail-open CSRF, F-029 missing JWK `kty` check, F-030 missing multi-`aud` `azp` check, F-031 missing CR/LF rejection in the redirect allowlist — all four Low, all FIXED). PoC method: scratch-DB + genuinely concurrent OS `php` CLI processes (busy-wait-synchronised) for F-027; pure-function unit tests for F-028 through F-031. See the Findings table and the coverage-ledger row below for the full write-up.

### 8. GDPR/CCPA data-subject rights — export + erasure (#37, epic #52, 2026-07-10)

**Files:** `_functions/fn_api_account.php` (`collectAccountExportData()`, `eraseUserAccount()`, `buildErasedAccountEmail()`, `handleAccountDataExport()`, `handleAccountErase()`), `public_html/api/v1/index.php`, `public_html/account/export/index.php`, `public_html/account/index.php` (no-JS "Delete my account" form)
**Trust boundary:** An already-authenticated caller's OWN account only — the same F-026 session-only boundary every other `account/*` route enforces, plus a NEW irreversible-destructive-action boundary (erasure) that additionally requires re-proving possession of the current password before any mutation, on top of an explicit `confirm: true` flag.
**Audited (self-review at build time, this stage):** own-account-only by construction (`resolveUserIdFromAuth($auth)` is the ONLY source of the target userID in both new functions — neither takes nor reads a client-supplied user identifier anywhere, verified by parameter-count/name reflection); session-only enforcement (`accountManagementAllowedFor($auth)` as the first statement in both HTTP handlers, identical F-026 pattern); export completeness vs. secrecy (every secret-bearing column — `passwordHash`, `apiKeyHash`, `tokensEncrypted`, the raw session token — statically confirmed absent from `collectAccountExportData()`'s own query/return shape, reusing the ALREADY-hardened `listUserSessions()`/`listLinkedOAuthProvidersForUser()`/`listApiKeysForUser()` helpers rather than a second, divergent implementation); erasure atomicity (a single MySQL transaction wraps the anonymizing `UPDATE`, the session/API-key/OAuth/QR-code mutations — a partial failure rolls back everything, never a half-anonymized account); erasure completeness (every documented PII column — email/displayName/firstName/lastName/avatarPath/passwordHash — is cleared/replaced, the avatar FILE is deleted from disk in addition to the DB pointer, ALL sessions/API keys/SSO links/saved codes are revoked/deactivated/unlinked/soft-deleted, never merely "the current one"); double-erase race guard (the anonymizing `UPDATE`'s `WHERE` re-checks `status != 'deleted'` in the SAME statement, reported as `409 ALREADY_ERASED` on zero affected rows rather than silently re-anonymizing or throwing); retention-vs-erasure boundary (confirmed via static regression guard that `eraseUserAccount()` NEVER writes to `tblSubscriptions`/`tblPayments` — those financial/audit rows are deliberately left untouched, relying on the pre-existing `ON DELETE RESTRICT` FK posture plus in-place `tblUsers` anonymization, rather than a `CASCADE`/manual-detach step that could silently break the audit trail); audit-log PII-freedom (the `account_erased`/`account_data_exported` `logActivity()` calls pass only the userID as `entityID` — no email/name/payload ever reaches `tblActivityLog`, confirmed both by static guard and live query after a real erasure).
**PoC method:** Static analysis (116 new `tests/test_account_data.php` assertions, incl. source-text regression guards on the exact SQL/transaction/guard shape) PLUS a full live scratch-DB (`cuercode_scratch_dsr`, dropped after use — no credentials file ever written, constants defined inline via a `php -S` `auto_prepend_file`) + real-HTTP-router pass with TWO independently-registered accounts (Alice, Bob), each with a saved QR code, Alice additionally holding a fully-scoped self-service API key. See the Coverage ledger row below for the complete evidence write-up.

**Strong baseline confirmed across all surfaces:** prepared statements throughout (`bind_param`, no string interpolation into SQL), `htmlspecialchars(ENT_QUOTES,'UTF-8')` on HTML output, CSRF + `hash_equals`, timing-safe API-key compare, UUID-v4 validation + `realpath` base-dir check on downloads, per-key/per-IP rate-limiting logic (inert due to schema bug — see F-014), secure session flags in bootstrap, deny-all `.htaccess` on all non-public directories, AES-256-GCM with random IV + auth-tag.
